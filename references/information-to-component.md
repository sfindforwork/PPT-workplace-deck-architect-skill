# Information relationship to component

Choose a component only after identifying the relationship the viewer needs to understand. The same content can require different layouts depending on whether the relationship is sequential, parallel, causal, or comparative.

| Information relationship | Useful component | Design requirement |
|---|---|---|
| sequential stages | numbered line or timeline | numbering and direction must make order unmistakable |
| rising capability or maturity | ascending path | stage height or position must visibly increase; do not use parallel columns that erase progression |
| process with decisions | flowchart | show roles, branches, closures, and exception handling; do not replace it with a generic loop |
| parallel categories | two-column layout or matrix | keep the same internal hierarchy in both columns |
| hierarchy | tree or nested levels | spacing should show parent-child relationships |
| comparison | comparison table | align the same dimensions before styling differences |
| multiple capabilities without measurements | labeled pentagon/framework | use labels and nodes; do not imply quantitative scores |
| measured multi-factor data | radar chart | show the scale, values, and source; never invent values for visual symmetry |
| evidence or screenshots | thumbnail strip, slideshow, or gallery | preserve source order and make full-resolution viewing available |
| summary with cause and response | stepped flow or nested sequence | show how 01 leads to 02 and 02 leads to 03; do not present dependent actions as peers |

## Path and timeline rules

- A straight line with numbered nodes is often clearer than a decorative route.
- Use one direction consistently. A left-to-right path should not change direction without an explicit reason.
- Keep the node, label, and description aligned as one unit.
- If the final stage is still in progress, label it as such instead of making an absolute claim.
- If one business requirement contains several product requirements, state that relationship explicitly without inventing a “sub-requirement” term the user did not use.

## Process and method rules

For a method page, make the method visible as a compact sequence, then use the lower area for the method's concrete rules or evidence. Do not mix background, method, and outcome into one undifferentiated list.

For a process page, preserve the user's actual terms for roles, states, decisions, and exceptions. A visually elegant flowchart with invented states is worse than a plain but faithful one.

## Image interactions

- Use a single lightbox for one independent image.
- Use a gallery when one node represents several related images; display them in source order, left to right where space permits.
- Bind the image trigger to the content node that explains it. Do not leave the image as an unrelated corner decoration.
- Keep the visible thumbnail's ratio and crop stable; the high-resolution view may use the original dimensions.
- Label the gallery with the relevant page or method, not a generic label from another section.

## Repeated ability components

If a deck has a repeated competency requirement—such as a role-level ability list—make it one reusable component. Use the same position and wording on each relevant page. Highlight only abilities actually exercised on that page; dim the rest. Do not repeat explanatory labels in several corners.
